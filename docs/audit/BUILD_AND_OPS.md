# TankoVault — Build / Dependency / Ops Hygiene Audit

Repo: `E:\Rust\manga-tracker-v3` · branch `main` @ `2c9a22e` · audited 2026-07-29
Scope: build system, dependencies, config, migrations, CI/CD, Docker/deploy, docs, observability.
Application-code security/architecture/frontend concerns are explicitly out of scope.

Verdict: the workspace is **well above average** for a hobby-scale Rust monorepo — genuine
workspace dependency unification, `unsafe_code = "forbid"`, clippy pedantic, cargo-deny +
cargo-audit in CI, a real sqlx offline-cache drift gate, an OpenAPI drift gate,
container-structure-tests, digest-pinned bases, and a shared service runtime that gives every
backend graceful shutdown + `/health` + `/ready` + a metrics port. It does **not** meet an
enterprise bar on four axes: a committed live secret, a CI gate that is silently red, a
documented-but-nonexistent Kubernetes deploy path, and no toolchain/dependency-update governance.

Severity counts: Critical 2 · High 7 · Medium 14 · Low 8.

## 1. Workspace hygiene

### 1.1 Committed live credentials in `deploy/local.env` — **Critical**

**Evidence** — `deploy/local.env:1-3` (file is git-tracked; `git ls-files deploy/local.env`
returns it; introduced in commit `e5cff29 feat(Frontend): improve anilink syncing`):

```
TANKOVAULT_ANILIST__CLIENT_ID: "46552"
TANKOVAULT_ANILIST__CLIENT_SECRET: "<REDACTED-ANILIST-CLIENT-SECRET>"
TANKOVAULT_ANILIST__TOKEN_ENCRYPTION_KEY: <REDACTED-AES-256-KEY>
```

`.gitignore:42-44` has `.env` / `.env.*` / `!.env.example` — none of which match the literal
filename `local.env`, so the guard was bypassed by naming. Contrast the surrounding hygiene:
`.dockerignore` explicitly excludes `.env*`, `*.pem`, `*.key`, and `deploy/docker-compose.yml:11-12`
carries a "Secrets here are DEV-ONLY placeholders" banner. This file is the one real secret and it
has no such banner.

The `TOKEN_ENCRYPTION_KEY` is a 32-byte base64 AES-GCM key (`aes-gcm` workspace dep, used by
`crates/auth` to seal AniList OAuth tokens at rest). If this key was ever used against a real
database, every stored AniList refresh token is decryptable by anyone with repo read access.

Note the file also uses YAML `key: value` syntax, not dotenv `KEY=value` — so it is not even
loadable by `docker compose --env-file`. It is a non-functional file that leaks a real secret.

**Why it matters** — Credential disclosure. Git history is immutable; deleting the file is not
sufficient.

**Remediation** (in order, all required):
1. Revoke/rotate the AniList OAuth application secret at anilist.co immediately.
2. Rotate `TANKOVAULT_ANILIST__TOKEN_ENCRYPTION_KEY` and re-encrypt or invalidate all rows in
   `external_accounts` holding sealed tokens.
3. Purge from history: `git filter-repo --path deploy/local.env --invert-paths` (or BFG), then
   force-push and have every clone re-clone.
4. Broaden the ignore rule and add a scanner gate:

```gitignore
# .gitignore — match by suffix, not just leading-dot
.env
.env.*
*.env
!*.env.example
!.env.example
```

5. Ship `deploy/local.env.example` with placeholder values only (see §7.2).

**Effort**: S (the fix); M (rotation + history rewrite coordination).

### 1.2 `crates/api-client/src/lib.rs` is 780 KB on a single physical line — **High**

**Evidence** — `crates/api-client/src/lib.rs`: `wc -l` = 1, `wc -c` = 780,181. Content begins
`// Generated by xtask. DO NOT EDIT.` then the entire progenitor output as one line:
`# [allow (unused_imports)] pub use progenitor_client :: { ... } ; # [allow (unused_imports)] use ...`.

`rustfmt.toml:1-6` claims the file is "spaced via `progenitor_impl::space_out_items`" — the
spacing evidently inserts spaces between tokens but no newlines. `xtask/src/main.rs:110`
regenerates it.

**Why it matters** — Every regeneration produces a single-line 780 KB diff: unreviewable in PR,
useless `git blame`, and a repository-size tax on every clone. It also directly causes finding
1.3. This is not a stub (the task brief's "1 LOC stub" premise is a line-count artifact) — the
crate is fully generated and genuinely consumed by `web/frontend/src/api/mod.rs:27` and the
console/sync views, so it must **not** be deleted.

**Remediation** — Emit real newlines in the generator and let rustfmt own the file, which removes
the need for the (broken) `ignore` entry entirely:

```rust
// xtask/src/main.rs, after progenitor generation
let tokens = generator.generate_tokens(&spec)?;
let ast = syn::parse2(tokens)?;
let src = prettyplease::unparse(&ast);   // add `prettyplease` + `syn` to xtask deps
std::fs::write(out, format!("// Generated by xtask. DO NOT EDIT.\n{src}"))?;
```

Then delete `rustfmt.toml` entirely (it contains nothing else) or replace its contents with real
style settings. Alternatively, generate into `OUT_DIR` via a build script and stop committing the
file at all — but that costs the offline/no-network build guarantee, so the prettyplease route is
preferred.

**Effort**: S.

## 2. Lints

### 2.1 `cargo fmt --all --check` is silently failing — CI's first gate is red — **Critical**

**Evidence** — reproduced locally with the stable toolchain the CI uses
(`dtolnay/rust-toolchain@stable`, `.github/workflows/ci.yml:32`):

```
$ rustfmt --version
rustfmt 1.8.0-stable (4a4ef493e3 2026-03-02)

$ cargo fmt --all --check
Warning: can't set `ignore = IgnoreList { path_set: {"crates/api-client/src/lib.rs"}, ... }`,
         unstable features are only available in nightly channel.
Diff in \\?\E:\Rust\manga-tracker-v3\crates\api-client\src\lib.rs:1:
...
$ echo $?
1
```

Exactly one file diffs: `crates/api-client/src/lib.rs`. The `ignore` key is the **only** content
of `rustfmt.toml` (`rustfmt.toml:6`) and it is a **nightly-only** rustfmt option. On stable it is
discarded with a warning, so the 780 KB generated file (§1.2) is formatted, diffs, and the step
exits 1.

**Why it matters** — `.github/workflows/ci.yml:41-42` runs `cargo fmt --all --check` as the first
step of the `lint` job. `lint` is a `needs:` prerequisite for `integration`, `docker`, and
`docker-frontend` (`ci.yml:114, 162, 227`). If this reproduces on the runner, **more than half the
pipeline never executes** — including every Docker build and the integration suite — and has not
since the file was generated. The entire CI story documented in `docs/` is unenforced.

The one scenario in which CI is green is if the runner's rustfmt version differs in behaviour;
that is UNVERIFIED from here (no access to Actions run history). Check the latest `main` run
before anything else — this finding is either "CI is broken" or "CI is one rustfmt bump away from
breaking", and both warrant the same fix.

**Remediation** — Fix the root cause (§1.2: make the generated file properly formatted, then
delete `rustfmt.toml`). As an immediate stopgap that works on stable, exclude via a crate-level
attribute instead of a nightly config key:

```rust
// crates/api-client/src/lib.rs — first line, emitted by the generator
#![cfg_attr(rustfmt, rustfmt::skip)]
```

…or scope the format check to the hand-written crates:

```yaml
      - name: rustfmt
        run: cargo fmt --check -p tankovault-domain -p tankovault-config -p tankovault-contracts \
               -p tankovault-service -p tankovault-db -p tankovault-fetch -p tankovault-solver \
               -p tankovault-adapters -p tankovault-auth -p tankovault-email -p tankovault-matcher \
               -p tankovault-bus -p tankovault-test-support -p tankovault-api \
               -p tankovault-control-plane -p tankovault-worker -p tankovault-notifier \
               -p tankovault-sync -p tankovault-challenge-solver -p tankovault-render \
               -p tankovault-frontend -p xtask
```

The `-p` list is brittle; prefer the generator fix.

**Effort**: S.

### 2.3 `#[allow(...)]` escapes: 36 total, concentrated in numeric casts — **Low**

**Evidence** — 36 occurrences across `crates/`, `services/`, `web/`. By lint:

| Count | Lint |
| --- | --- |
| 12 | `clippy::cast_possible_truncation` |
| 7 | `clippy::cast_precision_loss` |
| 6 | `clippy::too_many_arguments` |
| 2 | `clippy::too_many_lines` |
| 2 | `clippy::cast_sign_loss` |
| 1 each | `dead_code`, `clippy::unnecessary_wraps`, `clippy::result_large_err`, `clippy::needless_pass_by_value`, `clippy::match_same_arms`, `clippy::enum_variant_names` |

Worst offenders by file: `crates/db/src/repo/sync.rs` (3), then eight files with 2 each
(`crates/config/src/lib.rs`, `crates/matcher/src/lib.rs`, `web/frontend/src/util.rs`, …).

This is a **low** density for a workspace this size and the distribution is healthy — no blanket
`#![allow(clippy::pedantic)]` at a module root, no `dead_code` sprawl. The 21 cast-related allows
are the real signal: they cluster around `i64`↔`i32`↔`f64` conversions at the sqlx and scoring
boundaries.

**Why it matters** — Each `cast_possible_truncation` allow is a silent wraparound waiting for a
large row count or chapter number.

**Remediation** — Migrate `#[allow]` → `#[expect]` (stable since 1.81; this workspace is on 1.94)
so an allow that stops being necessary becomes a warning:

```rust
#[expect(clippy::cast_possible_truncation, reason = "row counts are bounded by LIMIT 500")]
```

Then add `#![warn(clippy::allow_attributes)]` to the workspace lints to prevent new bare `allow`s.
For the sqlx casts specifically, prefer `i64::try_from(...)` with an explicit error over a cast.

**Effort**: M.

## 3. Dependency risk (`deny.toml`)

### 3.1 All four `cargo-deny` sections are configured and enforced — no finding

`deny.toml` defines `[advisories]`, `[licenses]`, `[bans]`, `[sources]`, and
`.github/workflows/ci.yml:141-148` runs all four:

```yaml
      - uses: EmbarkStudios/cargo-deny-action@v2
        with:
          command: check advisories licenses sources bans
```

`[advisories].ignore = []` — **no advisories are being suppressed**, which is the correct posture
and better than most repos. `[sources]` denies unknown registries and unknown git sources with an
explicit crates.io allowlist. There is no `unmaintained = "allow"`-style softening. `cargo-audit`
runs as a second, independent gate (`ci.yml:150-157`).

### 3.2 `[bans]` warns rather than denies, with no explicit deny list — **Medium**

**Evidence** — `deny.toml:31-35`:

```toml
[bans]
multiple-versions = "warn"
wildcards = "warn"
```

Neither is a failure. There is no `deny = [...]` list, no `skip = [...]`, and no
`skip-tree = [...]`. Because `multiple-versions` is a warning, the 86 duplicates in §1.5 produce
warning noise that trains reviewers to ignore the section entirely.

**Why it matters** — A `warn` that fires 86 times is equivalent to no check. And with no `deny`
list, nothing prevents a transitive `openssl-sys` (which would break the `scratch` runtime at
exec time — the images ship no OpenSSL, only the musl loader + `libgcc_s`, per
`deploy/docker/cst/service.yaml`) or a `native-tls` from entering the graph. The workspace goes to
real trouble to stay rustls/BoringSSL-only
(`Cargo.toml:101, 153-158`) but does not enforce it.

**Remediation** — Convert to `deny` with an explicit, comment-justified skip list, and ban the
crates that would silently break the runtime contract:

```toml
[bans]
multiple-versions = "deny"
wildcards = "deny"
# Crates that must never enter the graph: the `scratch` runtime ships no OpenSSL and no OS
# CA store, and the crawl stack is BoringSSL-only. A transitive pull here fails at exec time,
# not build time — so catch it here.
deny = [
    { crate = "openssl-sys", reason = "scratch runtime has no OpenSSL; use rustls or wreq/BoringSSL" },
    { crate = "native-tls",  reason = "as above" },
    { crate = "openssl",     reason = "as above" },
]
# In-flight upstream transitions. Each entry MUST carry a reason and be re-reviewed quarterly.
skip = [
    { crate = "rand@0.8.7",   reason = "workspace pin; argon2 0.5 / aes-gcm 0.11 require it" },
    { crate = "rand@0.9.5",   reason = "transitive; drops when the RustCrypto 0.11 wave lands" },
    { crate = "digest@0.10.7", reason = "RustCrypto 0.10 -> 0.11 transition" },
    { crate = "sha2@0.10.9",   reason = "RustCrypto 0.10 -> 0.11 transition" },
    { crate = "hmac@0.12.1",   reason = "RustCrypto 0.10 -> 0.11 transition" },
    { crate = "getrandom@0.2.17", reason = "pulled by rand 0.8" },
    { crate = "syn@2.0.119",   reason = "proc-macro ecosystem mid-migration to syn 3" },
    { crate = "tower-http@0.6.11", reason = "transitive; workspace pins 0.7" },
]
skip-tree = [
    { crate = "windows-sys", reason = "Windows-only dev dependency trees" },
    { crate = "testcontainers", depth = 5, reason = "dev-only integration harness" },
]
```

**Effort**: M (the skip list needs one pass to converge).

### 3.4 No lockfile-integrity or supply-chain-provenance gate — **Medium**

**Evidence** — CI never runs `cargo update --locked --dry-run`, `cargo vet`, or
`cargo-auditable`. `Cargo.lock` is committed (152 KB) and builds use `--locked`
(`deploy/docker/Dockerfile:88, 94`) — good — but nothing verifies that a PR did not quietly bump a
transitive dep, and shipped binaries carry no embedded dependency manifest.

**Why it matters** — With `cargo-auditable` a shipped `scratch` binary can be scanned post-hoc
(`cargo audit bin`); without it, a running container cannot be mapped back to its dependency set —
which matters precisely because these images have no package manager for a scanner to interrogate.

**Remediation** — Add `cargo-auditable` to the Docker builder stage (one-line change, produces a
drop-in replacement for `cargo build`):


### 5.1 The `wreq`/BoringSSL dlopen constraint is handled robustly — no finding

The constraint is correctly diagnosed and correctly solved, and — unusually — the *reasoning* is
recorded at the point of decision (`Dockerfile:37-57` and `70-81`):

- Alpine builder rather than Debian, because Debian's `musl-tools` gives `musl-gcc` only (no musl
  C++ compiler, no musl `libstdc++`) and BoringSSL needs C++. Alpine *is* musl, so stock `g++` is
  already the right target.
- **Native build, no `--target`**, because `boring-sys` runs `bindgen`, which `dlopen`s
  `libclang` at build-script time; musl defaults to `+crt-static` and a statically linked build
  script cannot `dlopen`. Crucially, the comment records the non-obvious reason a cross build
  cannot fix it: *"`RUSTFLAGS` is not applied to host build scripts when `--target` is passed."*
- `ENV RUSTFLAGS="-C target-feature=-crt-static"` (`Dockerfile:81`) as the consequence, and the
  resulting musl-dynamic binary's exact three runtime dependencies enumerated and baked in
  (`Dockerfile:137-139`).
- `LIBCLANG_PATH=/usr/lib` (`Dockerfile:57`) because bindgen does not search Alpine's lib dir.
- CI installs `cmake nasm libclang-dev` explicitly on **all five** Rust jobs rather than relying
  on the runner image (`ci.yml:39-40, 53-54, 97-98, 119-120`).
- `cst/service.yaml` asserts the loader and `libgcc_s` exist, with a comment noting that without
  them the container fails at exec with a bare "no such file or directory".

The only residual risk is the `runtime-browser` stage's musl-loader-on-glibc arrangement
(`Dockerfile:114-116`), which routes musl's `libgcc_s` into `/usr/lib/musl` via
`/etc/ld-musl-x86_64.path` so it cannot shadow the glibc `libgcc_s` Chromium loads. This is
correct but fragile against a Debian base bump; it is covered by `cst/render.yaml`.

### 5.3 No container healthchecks and no resource limits on app services in compose — **Medium**

**Evidence** — `grep -c healthcheck deploy/docker-compose.yml` → 5, all on infrastructure
(`postgres:35`, `redis:44`, `nats:54`; `flaresolverr` has none either). Zero of the eight
TankoVault services declare `healthcheck:`. The only `deploy:` block is
`docker-compose.yml:188-189` (`worker` `replicas: 2`) — no `resources.limits`, no
`reservations`, anywhere.

The compose file at `:250-255` justifies the healthcheck absence: *"Like the other services it is
a static musl binary on `scratch` (no shell), so — matching them — it carries no container
healthcheck."* That reasoning is sound for `CMD-SHELL` but **not** for Docker healthchecks in
general: `scratch` blocks shell-based probes, but the services all expose `/health` and `/ready`
already (§8), so the ordering guarantee is simply left on the table.

Consequently `depends_on: { api: { condition: service_started } }`
(`docker-compose.yml:266-267`) means the frontend starts as soon as the API **process** exists,
not when it is ready — a startup race on every `compose up`.

**Why it matters** — No memory limit on `worker` (which parses arbitrary provider HTML with
`scraper`) or on `render` (which drives a full Chromium) means a single pathological page can OOM
the host and take down Postgres with it. No `service_healthy` conditions means flaky cold starts.

**Remediation** — Add limits to every service and healthchecks where a probe is reachable. Docker
healthchecks on `scratch` need a probe binary; the cheapest fix is to add a `--health-check`
subcommand to the service binary itself (it already has an HTTP client), then:

```yaml
  api:
    healthcheck:
      test: ["CMD", "/usr/local/bin/tankovault-service", "--health-check"]
      interval: 10s
      timeout: 3s
      retries: 6
      start_period: 20s
    deploy:
      resources:
        limits: { cpus: "2.0", memory: 512M }
        reservations: { memory: 128M }

  worker:
    deploy:
      replicas: 2
      resources:
        limits: { cpus: "2.0", memory: 1G }

  render:                      # Chromium — the memory hog
    deploy:
      resources:
        limits: { cpus: "2.0", memory: 2G }
    shm_size: 1gb              # Chromium crashes on the default 64M /dev/shm

  frontend:
    depends_on:
      api: { condition: service_healthy }   # was: service_started
```

Note `shm_size` for `render` is independently required — headless Chromium in a container reliably
crashes with the default 64 MB `/dev/shm`. UNVERIFIED whether `--no-sandbox`
(`Dockerfile:120-121`) plus chromiumoxide's default flags already include
`--disable-dev-shm-usage`; if not, this is a latent crash.

### 6.2 Zero reversibility: no `.down.sql` for any migration — **Medium**

**Evidence** — `ls migrations/*.down.sql` → none. All 19 files are sqlx *simple* (up-only)
migrations. `xtask` offers `migrate`, `reset`, `seed`, `openapi`, `sqlx-prepare` — `reset` is

**Why it matters** — There is **no rollback path in production**. A bad migration can only be

(§6.3), and because nothing in `docs/OPERATIONS.md` describes a backup/restore procedure to fall

**Remediation** — Convert to sqlx reversible migrations
(`sqlx migrate add -r <name>` produces `.up.sql`/`.down.sql`) going forward. Retrofitting down
scripts for 0001–0019 is not worth it; instead document the rollback procedure explicitly:

```md
## Rollback
Migrations are up-only. Rolling back a release that includes a migration requires a
point-in-time restore. Before any deploy containing a new `migrations/*.sql`:
1. `pg_dump -Fc` the database and verify the dump restores into a scratch instance.
2. Record the `_sqlx_migrations` high-water mark.
3. Deploy. On failure, restore the dump — do not hand-edit `_sqlx_migrations`.
```

Additionally, adopt the expand/contract pattern so destructive steps ship one release *after* the
code that stops using the column.

**Effort**: M.

### 6.4 No `CREATE INDEX CONCURRENTLY` on tables that will grow large — **Medium**

**Evidence** — 30 `CREATE INDEX` / `CREATE UNIQUE INDEX` statements across the migration set;
**zero** use `CONCURRENTLY`. The ones on tables that grow without bound:

| Migration | Statement | Table growth |
| --- | --- | --- |
| `0003_catalog.sql:84` | `chapters_source_idx ON chapters (series_source_id, number DESC)` | one row per chapter per provider — the largest table |
| `0003_catalog.sql:85` | `chapters_discovered ON chapters (discovered_at DESC)` | as above |
| `0003_catalog.sql:35-36` | `series_search_gin` (GIN), `series_title_trgm` (GIN trgm) | GIN builds are the slowest of all |
| `0004_users.sql:50` | `notifications_user_unread ON notifications (user_id, created_at DESC)` | unbounded fan-out table |
| `0007_moderation.sql:28-29` | `audit_log_actor_idx`, `audit_log_action_idx` | append-only, 365-day retention default |
| `0017_audit_and_privacy.sql:28` | `audit_log_created_idx ON audit_log (created_at)` | added to an **already-populated** `audit_log` |
| `0012_sync_remote_entries.sql:25` | `sync_remote_entries_unmatched_idx` | grows with AniList library size × users |

`0003`/`0004`/`0007` create the index at the same time as the table, so they are harmless (empty
table). The genuinely risky one is **`0017_audit_and_privacy.sql:28`**: it adds an index to
`audit_log`, a table created back in `0007` and written on every privileged action. A non-concurrent
`CREATE INDEX` takes an `ACCESS EXCLUSIVE`-blocking `SHARE` lock, stalling every audit write for
the duration of the build.

**Why it matters** — On a populated `audit_log` this is a write outage of unbounded length during
deploy.

**Remediation** — For future index additions to populated tables, use a separate migration
containing only:

```sql
-- sqlx runs each migration in a transaction by default; CONCURRENTLY cannot run in one.
-- This file must be marked no-transaction.
CREATE INDEX CONCURRENTLY IF NOT EXISTS audit_log_created_idx ON audit_log (created_at);
```

sqlx supports this via a `-- no-transaction` directive as the **first line** of the migration file.
Verify against your sqlx 0.9 version before relying on it. Also add the sibling guard: a
`CONCURRENTLY` build that fails leaves an `INVALID` index behind, so the runbook must include
`DROP INDEX CONCURRENTLY IF EXISTS <name>;` before retry.

**Effort**: S (process) — no retroactive change needed.

### 6.5 Non-idempotent DDL: `CREATE TABLE` / `CREATE TYPE` without `IF NOT EXISTS` — **Low**

**Evidence** — `0001_extensions.sql:8-9` correctly uses `CREATE EXTENSION IF NOT EXISTS`. Every
other object does not: `0002_enums.sql:2-10` (10 × `CREATE TYPE`), all 20 `CREATE TABLE`
statements, all 30 `CREATE INDEX` statements.

**Why it matters** — Low in practice: sqlx's `_sqlx_migrations` ledger plus its advisory lock
means a migration never runs twice. `IF NOT EXISTS` would matter only for manual replay or a
corrupted ledger. Note `CREATE TYPE` has no `IF NOT EXISTS` form in Postgres at all, so `0002`
cannot be fixed even in principle without a `DO $$ ... EXCEPTION WHEN duplicate_object $$` block.

**Remediation** — Add `IF NOT EXISTS` to `CREATE TABLE`/`CREATE INDEX` in **new** migrations as a
cheap belt-and-braces. Leave 0001–0019 alone: editing an applied migration changes its checksum
and breaks `sqlx migrate run` on every existing database.

**Effort**: S.

### 7.3 Startup validation is thin and lives in one service only — **Medium**

**Evidence** — `crates/config/src/lib.rs` has **no** validation beyond serde deserialization: no

(`ConfigError` at `lib.rs:21` covers parse/IO only). The `validator` crate is declared in
`[workspace.dependencies]` (`Cargo.toml:126`) and used by **nobody** (§1.4).

The one real check is in `services/api/src/main.rs:102-144`, and it is well-written:

```rust
const MIN_JWT_SECRET_LEN: usize = 32;
// "A production deployment that boots with a missing or weak `jwt_secret` can have every
//  session forged... `password_pepper` is a weakened — not broken — posture"
if auth.jwt_secret.len() < MIN_JWT_SECRET_LEN { /* warn in dev, error in prod profile */ }
if auth.jwt_secret.trim().is_empty() { /* hard error */ }
```

But nothing equivalent exists for: `TANKOVAULT_ANILIST__TOKEN_ENCRYPTION_KEY` (must be exactly 32
bytes after base64 decode — a wrong length is an AES-GCM key-construction failure at first use,
not at boot), `TANKOVAULT_DATABASE__URL` (unset → figment "missing field" with no hint about the
`__` nesting convention), `TANKOVAULT_EMAIL__*` (a partial config silently falls back to the no-op
mailer per `docker-compose.yml:106-107` — so password reset silently stops working), or
`TANKOVAULT_RATE_LIMIT__BACKEND=redis` with no `TANKOVAULT_REDIS__URL`.

**Why it matters** — Misconfiguration surfaces at first use in production rather than at boot.
The email case is the worst: a silent degradation to a mailer that "logs + drops", which an
operator will not notice until a user reports a missing password-reset email.

**Remediation** — Add a `Validate` trait to `crates/config` and call it in `load()`:

```rust
pub trait Validate { fn validate(&self) -> Result<(), ConfigError>; }

pub fn load<T: DeserializeOwned + Validate>() -> Result<T, ConfigError> {
    let cfg: T = Figment::new()./* ... */.extract()?;
    cfg.validate()?;
    Ok(cfg)
}
```

At minimum validate: encryption-key length after base64 decode; `rate_limit.backend == Redis`
implies `redis.url.is_some()`; email is all-or-nothing (and log at `warn!` when falling back to
the no-op mailer, rather than silently); `cors.allow_credentials` implies a non-empty
`allowed_origins`. Every message should name the offending **env var**, not the Rust field —
figment's default errors do not translate `database.url` back to
`TANKOVAULT_DATABASE__URL`.

### 8.1 `frontend` service bypasses the shared runtime — **Medium**

**Evidence** — `services/frontend/src/main.rs:110-140` and `143-175`:

- Health: `.route("/healthz", get(healthz))` (`main.rs`, in `build_router`) — a **different path**
  from the `/health` + `/ready` contract every other service exposes, and there is no readiness
  probe at all, so nothing checks whether the `api` upstream is reachable.
- No `spawn_metrics_server` call → **no `/metrics` scrape** for the tier that fronts every user
  request. Proxy latency, error rate, and SSE connection count are unobservable.
- Uses a bare `.layer(TraceLayer::new_for_http())` instead of `tankovault_service::HttpStack` →
  **no request-id generation or propagation**, so a request cannot be correlated across the
  frontend → api hop. This is exactly the correlation the rest of the stack is built for.
- No rate limiting, no body-size cap layer, no timeout layer (though `max_body_bytes` and
  `connect_timeout_secs` are handled manually in the proxy handler).

`deploy/README.md:109-111` already asserts *"k8s HTTP probes are wired against each service's
`/health` and `/ready` (the frontend's ...)"* — the sentence trails into the nonexistent Helm docs
(§5.2), so the inconsistency is acknowledged but unresolved.

**Why it matters** — The single most user-facing service is the least observable one, and it is
the origin point of every request-id chain. Any orchestrator config templated on `/health` will
fail against the frontend.

**Remediation** — Adopt `HttpStack` in `services/frontend/src/main.rs`:

```rust
let health = Health::builder()
    .check(HttpCheck::new("api", format!("{}/health", state.upstream)))  // readiness = upstream reachable
    .build();
let metrics = MetricsRegistry::from_config(&cfg.metrics)?;
tankovault_service::spawn_metrics_server(metrics.clone(), shutdown.clone());
let app = HttpStack::new(&cfg).health(health).metrics(metrics).build(build_router(...));
```

Keep `/healthz` as an alias for one release if anything depends on it, then remove.

**Effort**: S.

### 9.2 No breaking-change detection on the spec — **Medium**

**Evidence** — `openapi --check` detects *drift between the code and the committed artifacts*. It

**Why it matters** — The SPA is deployed separately from the API (different images, different
compose services), so a version skew window always exists. A breaking spec change ships silently
and manifests as runtime deserialization failures in the browser.

**Remediation** — Add a diff gate against the base branch's spec:

```yaml
  openapi-breaking:
    name: openapi breaking changes
    runs-on: ubuntu-latest
    if: github.event_name == 'pull_request'
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }
      - name: base spec
        run: git show "origin/${{ github.base_ref }}:openapi.json" > /tmp/base.json
      - uses: oasdiff/oasdiff-action/breaking@main
        with:
          base: /tmp/base.json
          revision: openapi.json
          fail-on: ERR
```

### J. `.github/workflows/release.yml` — new file

```yaml
name: Release

on:
  push:
    tags: ["v*"]
  workflow_dispatch:

permissions:
  contents: read
  packages: write
  id-token: write        # cosign keyless signing

jobs:
  publish:
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix:
        bin: [api, worker, control-plane, notifier, sync, challenge-solver, render, xtask]
    steps:
      - uses: actions/checkout@v4
      - uses: docker/setup-buildx-action@v3
      - uses: sigstore/cosign-installer@v3
      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - name: derive SOURCE_DATE_EPOCH
        run: echo "SOURCE_DATE_EPOCH=$(git log -1 --format=%ct)" >> "$GITHUB_ENV"
      - id: meta
        uses: docker/metadata-action@v5
        with:
          images: ghcr.io/${{ github.repository }}/${{ matrix.bin }}
          tags: |
            type=semver,pattern={{version}}
            type=semver,pattern={{major}}.{{minor}}
            type=sha,format=long
      - id: build
        uses: docker/build-push-action@v6
        with:
          context: .
          file: deploy/docker/Dockerfile
          build-args: |
            BIN=${{ matrix.bin }}
            SOURCE_DATE_EPOCH=${{ env.SOURCE_DATE_EPOCH }}
          target: ${{ matrix.bin == 'render' && 'runtime-browser' || 'runtime' }}
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}
          # SBOM matters more than usual here: `scratch` images cannot be scanned by
          # package-manager-based tooling, so this is the only bill of materials.
          sbom: true
          provenance: mode=max
      - name: sign image (keyless)
        run: cosign sign --yes "ghcr.io/${{ github.repository }}/${{ matrix.bin }}@${{ steps.build.outputs.digest }}"
      - name: scan image
        uses: aquasecurity/trivy-action@master
        with:
          image-ref: ghcr.io/${{ github.repository }}/${{ matrix.bin }}@${{ steps.build.outputs.digest }}
          exit-code: "1"
          severity: CRITICAL,HIGH
          ignore-unfixed: true
```

Note `provenance: mode=max` here contradicts the `provenance: false` used in `ci.yml` for
byte-reproducibility. That is the correct split: CI proves reproducibility, release provides
attestation.
